# 个人应用开发规范

状态：候选规范 0.2；BugChecking UI-U0～UI-U3 已验收，固定配色与无底色一级外壳增量待真机验收，UI-U4 尚未验收；跨项目倾向仍待天色 beta
适用者：产品所有者本人及协作 AI／开发者
当前证据：BugChecking Android；跨项目规则尚未全部验证

## 1. 规范目的

本规范定义“怎样的应用像我做的”，同时约束从需求、设计、实现到真机验收的流程。它不把个人工具强行改造成面向大众的商业产品，也不允许用“个人使用”为理由忽略功能正确性、数据安全、视觉可读性和平台稳定性。

规则分为四类。准备进入 `DESIGN`、记忆或 skill 的规范性规则必须进入下方规则登记表，标注类别、作用域、状态、证据、例外、晋级条件和替代关系；正文其余内容是对登记规则的解释，不自动成为独立规范：

- **E（工程底线）：** 所有项目强制，不可被个人工具定位豁免。
- **P（已确认个人倾向）：** 用户明确提升为个人偏好，或在至少两个项目稳定验证；必须写明适用模式，例如“仅个人工具”。
- **B（项目边界合同）：** 只约束明确命名的单一项目；本稿当前的 B 项均属于 BugChecking，天色可建立自己的 B 项，默认永不跨项目推广。
- **C（候选个人倾向）：** 有跨项目假设，但需天色 beta 证据或用户明确提升；验证失败仍可保留为 B 类。

类别与状态正交：C 可以在某次项目实验中成为 `accepted`，但仍只是已接受的候选，不能自动变成 P；`verified` 表示约定的自动／真机证据通过，`accepted` 还需要用户明确确认；有条件通过保持 `verified`；`superseded` 是保留替代链的终止状态。C 提升为 P 是 Gate M 的独立决定，不与单项目验收捆绑。

当前已确认的 P 类包括：个人工具允许少说明、图标优先和低成本隐藏手势；特色次要动作不应仅因“不是主功能”就被藏起来；配色强调按真实操作重要性分配，而不是跟随组件名称或前端层级。具体色号和 BugChecking 视觉世界仍是 B 类，明亮柔和配色、带色深色表面、系统字体优先等仍是 C 类。

**不可豁免规则。** “个人工具”只能调整引导密度、视觉表达和交互显性程度，不得降低数据正确性、可恢复性、权限与隐私安全、平台稳定性、硬件安全及必要的可操作性。

## 2. 我的产品倾向

### 2.1 产品定位

- 默认先判断应用是个人工具、面向熟练用户的工具，还是面向公众的产品；三者不得共用一套 onboarding 与解释密度。
- 个人工具允许学习成本、隐藏手势和图标优先，只要状态反馈明确、误操作成本可控并有恢复方式；不要求为遗忘后的发现性增加常驻提示。
- “简单”不等于“没有个性”。少量非核心特色功能可以为了可玩性长期保留，并在主界面持续可见。
- 不为假设中的新用户增加教程、帮助段落和重复按钮名称。
- 解释文字只用于错误恢复、权限原因、不可逆／高成本操作、诊断信息和状态本身无法表达的歧义。

### 2.2 视觉气质

- **C 类候选：** 偏好明亮但不过饱和、柔和但不灰脏的色彩；避免泥灰、纯黑大面积表面和默认模板蓝。
- 动态取色不是目标本身；当它削弱产品识别或操作层级时，优先使用经过浅／深色真机验证的固定品牌色板。
- **C 类候选：** 深色模式偏好经过设计的表面关系，而不是简单黑底反相；BugChecking 当前炭黑／灰粉体系是项目专属 B 类。
- 强调色的稀缺性由真实任务决定：先列核心状态／动作、特色状态和普通辅助动作，再分配颜色；同一界面避免多种相近色表达同一层级。
- 喜欢有一层可识别的环境背景或主题纹理，但正文和控件必须有安静、可读的局部表面。
- 玻璃／半透明只按角色使用，不平均铺满所有层级；摘要和选中可以更有表现力，表单应更稳定、不透明。
- 不依赖渐变、光晕、装饰卡片或无意义插画制造“高级感”。

### 2.3 布局与信息密度

- 在触屏任务页中优先建立一个视觉主动作；仪表板、对称选择或多窗格工具可有经 brief 说明的例外。特色次要功能可以持续可见，但必须降级而不是藏起来。
- 偏好稳定、整齐、可预测的列表节奏。卡片高度可作为视觉秩序的一部分，不应被任意长文本破坏。
- 轨迹卡等紧凑信息卡优先单行尾部省略；需要查看全文时在编辑态、详情态或主动触发后显示。
- 内容起点、页面水平 inset、卡片 padding 和底部安全区要跨页面一致。
- 稀疏页面允许留白；高密度表单不使用装饰性空白拉长任务。
- 在移动端，有状态、可恢复、可滚动、多步骤或异步流程优先使用独立页面；短确认和短选择使用 Dialog／Bottom Sheet。桌面和多窗格产品按平台模式另定。

### 2.4 字体与排版

- **C 类候选：** 优先平台系统字体，尤其重视中文、拉丁字符、数字和符号的完整覆盖；品牌型项目可用经过字形、性能和授权验证的字体推翻该候选。
- 使用语义 type roles，不在页面中散落一次性字号和字重。
- 层级优先通过字号、字重、间距和容器建立；透明度不是默认的次要文字方案。
- 数值与单位是原子内容，不在换行时拆开。
- 当组件合同要求固定高度时，长标题使用尾部省略，禁止自动换行；主动 marquee 必须有触发条件且尊重减少动态效果。
- 表单标签在输入后仍可见；错误靠文字／图标与语义色共同表达。

### 2.5 控件与选择器

- 优先平台原生和项目已有设计系统；Android 项目优先 Material 3，不为了“独特”自造陌生基础控件。
- 图标优先适用于熟悉、低成本、个人使用的动作；外部用户、不可逆动作或诊断流程再考虑文字标签。
- Android 上可用 Filled/FAB、tonal、outlined/text 表达结构和交互类型，但组件变体不自动获得强调色。先按实际任务重要性分级，再用组件级 colors/token 映射；破坏性动作与日常动作在位置、色调或容器上分离。
- Android／触屏目标至少 48 × 48 dp；其它平台遵循对应平台目标尺寸。
- 隐藏手势可以成为特色交互，但必须满足：触发后立即有反馈、状态可见、不会与常规点击冲突、失败可恢复且不会造成不可恢复后果。
- 选择器优先展示完成当前决策所需的最少字段，但必须保留足够的消歧信息；地点候选不堆叠无用 metadata，也不能因过度精简而选错对象。

### 2.6 动效与声音

- 动效解释状态变化，不做环境编舞；偏好短、克制、有界的 spring。
- 持续动画只在确有工作进行时存在，例如同步旋转。
- 完成、收藏分级等可以有轻微新奇感，但不能掩盖最终状态。
- 遵守系统动画时长／减少动态效果设置。
- 声音和触觉用于确认关键状态，不为普通浏览制造噪音。

### 2.7 外部资源与依赖

- 优先使用平台能力、成熟维护的库和已有设计系统；新增依赖必须说明解决的问题、许可证、体积、维护状态和替代方案。
- 地图、图表等坐标型内容优先交给渲染器的原生 source/layer 或投影 API；禁止在 UI 层重复实现投影数学，但允许调用渲染器提供的坐标转换完成命中测试和验收。
- 图标保持同一家族；Android／Material 3 项目优先 Material 图标。新增自定义图标必须匹配线宽、视口、圆角和视觉重量。
- 图片、字体、地图和第三方素材必须记录来源、许可证、署名要求和离线／失败策略。
- 不下载通用装饰素材填空；外部资源必须承担内容、识别或功能价值。
- 中文字体必须先验证字形覆盖，再讨论风格；编译成功不代表真机能够显示。

## 3. 通用工程底线

- 产品声明定义“想要什么”，真机实测定义“实际发生什么”，二者不能互相覆盖。实现事实优先级为真机实测 > 当前代码／资源 > 历史说明；产品意图优先级为用户当前明确声明 > 当前权威设计／协议文档 > 历史偏好。意图与现实冲突时记录为缺陷或待决策，不做同级取舍。
- 不把审美建议伪装成功能缺陷；不把商业产品默认规则强加给个人工具。
- 不可逆操作、数据迁移、同步协议、BLE 语义和兼容性必须单独批准，不能通过 UI 改动顺手引入。
- 数据显示必须忠实：坐标、顺序、单位、时间和状态不能为了视觉整齐而改变事实。
- 代码通过编译不等于视觉、手势、字体、地图或硬件行为通过。
- 保留用户已有修改；每次实现前记录工作区状态，验证只触及当前范围。
- 所有候选标准必须有状态：`proposed`、`verified`、`accepted`、`superseded`。

## 4. BugChecking 项目专属合同（B 类）

- 视觉识别保留居中裁切城市地图、旅程带与糖果撞色；UI-U3.5 正以固定杏橘／玫瑰桃、炭黑／灰粉、荧光绿／糖果红替代旧动态柔糖／夜雾具体色板，验收前状态为 `proposed`，不得机械复制到天色 beta。
- 一级访问由底栏／rail 的轨迹、清单、二维码和左上头像“设备与我”组成；轨迹卡整卡进入编辑，地点名固定单行省略并保持等高。
- 地图与地点库是持续可见的特色次要入口；添加是唯一主 FAB。
- 定时长按是主要收藏交互，可保持隐蔽；三段反馈必须在脉冲、轨迹卡、地点库和地图星标中共用一套清晰可辨的糖果红等级色，荧光绿只承担动作强调。新收藏场所会立即关联无歧义匹配的历史轨迹，但批量迁移及 BLE／同步语义仍需独立批准。
- 清单不显示序号和排序按钮；长按只在组内排序并持久化。
- 外部 UI、文档、APK／固件产物、发布名称和 BLE 广播默认使用 `BugChecking`；legacy BLE 识别、数据库、协议字段、类名和 `passport_*` 内部符号在独立迁移前保留兼容。
- 选择附近地点只修改显示名称，保留真实打卡坐标。
- 透明根 Scaffold 显式使用 `onSurface`；高密度表单表面保持稳定、不透明。轨迹添加／编辑页顶栏只保留标题，精度放在坐标附近，不使用重复状态副标题。
- 固定底部保存／添加动作使用透明承载层，并按实测高度避让 navigation／IME；不增加全宽 tonal 色块。系统栏保持 edge-to-edge 且随主题自适应。
- 地图署名使用可读语义 scrim 并消费 safe-drawing inset；点位／轨迹线由 renderer source／layer 持有，普通点为圆形、收藏点为五角星。UI-U2 已验收，但原生聚类 token 仍延期。
- 当前 UI-U4 前置外壳中，一级页面不使用实体顶栏或页面标题。设备入口是最高价值状态／动作：容器保持中性，断联图标深绿，其余连接／同步图标荧光绿；普通编辑辅助动作、完成度／二维码卡片底色、资料与备份动作保持中性，旅程与清单进度使用糖果红。

## 5. 已发生的方向变化与返工

### 5.1 旧色板被“动态柔糖／夜雾”替代

**发生了什么。** 早期 Route Blue／Passport Ink 等静态方向建立后，真机观感被认为偏灰、偏泥，随后改为更明亮、适中彩度的动态柔糖和蓝灰夜雾，并完成历史 Android Phase 3 验收。

**返工原因。** 色板决策早于目标设备上的完整浅／深、动态／静态对照验收，旧方案被文档化后又被正式替代。

**流程修正。** 颜色方向在成为基线前必须提供目标设备上的成组样张；新基线必须显式写明 `supersedes`，旧值不得继续作为并列真相来源。

### 5.2 收藏功能曾把多层问题混在一起

**发生了什么。** 收藏等级同时牵涉视觉、长按交互、数据库、BLE、固件协议、迁移和同步语义，因此早期被整体推迟。后来用户确认隐藏长按和地点库属于产品特色，但协议与迁移仍未自动获批。

**返工原因。** 一个“功能”没有拆成 UI、数据、协议和兼容性四层审批，导致任何一层不确定都会阻塞全部工作。

**流程修正。** 每个跨端功能先画边界表；允许 UI/交互先验收，但不得暗示数据和协议已经接受。

### 5.3 审计曾误用大众 App 假设

**发生了什么。** 初版审计把主要受众写成普通新用户，因而建议更多文字入口、空状态 CTA 和显式收藏选择器。用户随后明确这是个人工具，隐藏与新奇是有意选择。

**返工原因。** 审计开始前没有先冻结受众、使用频率、误操作成本和非目标。

**流程修正。** 所有设计工作先写四行 brief：谁使用、是否公开、失败成本、哪些体验明确不优化。通用 UX 规则只能在能说明实际代价时成为缺陷。

### 5.4 FAB 通用建议差点伤害产品特色

**发生了什么。** “每页一个 FAB”是正确的层级判断，但若把地图和地点库藏入菜单，会牺牲少数具有可玩性的特色。

**返工原因。** 只区分主／次动作，没有区分“特色次要动作”和普通工具动作。

**流程修正。** 动作清单分为主动作、特色次要动作、普通次要动作、破坏性动作；特色次要动作可以持续可见，但不得伪装成主动作。

### 5.5 通用长文本建议与等高卡片冲突

**发生了什么。** 自动换行通常能展示完整文本，但轨迹卡要求稳定等高。当前实现实际已使用单行省略，用户确认不允许长地点名改变卡片高度。

**返工原因。** 没有在组件级记录 overflow contract，就直接套用“长文本应该回流”的通用建议。

**流程修正。** 每个数据组件在开发前明确：最大行数、溢出方式、全文入口、极端样本和字体倍率行为。

### 5.6 静态截图审计漏掉地图动态故障

**发生了什么。** 地图页面被截图审计，但缩放过程中点位／轨迹线消失或错位没有被发现。

**返工原因。** 对自定义渲染只检查静态构图，没有检查 zoom、pan、rotate、重建和竞态。

**流程修正。** 任何自定义地图、图表、Canvas、动画或手势必须有动态状态矩阵；静态截图不能签署功能正确性。

### 5.7 地名清洗曾接近“先写规则、后找证据”

**发生了什么。** 对 Geocoder 拼接名称，按“酒店”“苑”等后缀拆分看似快速，却可能破坏真实商户名，最终决定暂缓并先收集原始字段和同坐标多条 Address。

**返工原因。** 从一个异常样本直接抽象字符串规则，缺少数据来源诊断和反例测试。

**流程修正。** 数据清洗必须先记录原始字段、样本分布、优先级和反例，再实现规则；没有测试不得推广。

### 5.8 品牌改名不能机械替换内部兼容名

**发生了什么。** 外部产品统一为 BugChecking，但 `passport_*`、数据库、协议字段和旧 BLE 名称仍有兼容职责。

**返工风险。** 把品牌一致性误解为全仓库机械替换，会破坏设备与历史数据兼容。

**流程修正。** 每次重命名先分外部展示、公开构建产物／发布、BLE 广播、协议、数据库和历史文档；前三层默认跟随新品牌，legacy 识别与内部协议／数据库迁移另立计划。

### 5.9 底部动作 Surface 与系统导航栏曾被混为一层

**发生了什么。** 初次判断把保存／添加按钮外的 tonal Surface 当成界面割裂的主因；用户指出 Android 强制黑／白导航栏色块是独立且更重要的适配缺陷。完成 edge-to-edge 修复后，用户又单独决定去掉应用层 Surface。

**返工原因。** 评审没有把按钮本体、应用容器、系统栏背景和 inset 归属拆开，导致不同层的问题与偏好被混在同一次判断里。

**流程修正。** 后续真机评审逐层标注这四项，每次只改一个变量，并在浅／深色下成组截图；后来的偏好调整不能反向证明早先诊断正确。

### 5.10 只改画布造成了“负优化”

**发生了什么。** 为降低浅色模式刺眼感，先只把纯白画布压灰，结果原本带玫瑰暖意的卡片、顶／底栏和编辑工具表面反而显得苍白，旅程线与地图遮罩也失去整体关系。

**返工原因。** 把背景色当作孤立 token 调整，没有把画布、地图遮罩、chrome、卡片、边界、文字和旅程线作为同一张合成图评审。

**流程修正。** 任何大面积 surface 变更必须成组调整并截图比较完整页面；验收问题包括屏幕是否减眩、内容层是否仍清晰、品牌暖意是否保留、路线／边界是否仍可辨。

### 5.11 组件默认色制造了错误的重要性

**发生了什么。** 统一 primary／secondary 为荧光绿后，Filled、TonalButton、Slider 和默认图标自动获得同一强调色；编辑辅助动作、完成度卡片、二维码卡片与资料／备份操作因此和设备同步入口争夺注意力，并出现多个相近绿色像 bug 一样并列。

**返工原因。** 先按前端组件层级分配色彩，再倒推产品重要性；没有先建立用户操作重要性地图。

**流程修正。** 配色前先列出“核心状态／动作、特色状态、普通辅助动作、危险动作”；全局 palette 只提供原料，页面用语义／组件 token 明确分配。相近色只有在承担不同且可命名的状态语义时才能共存。

## 6. 标准开发流程

Gate 不是按字母顺序无条件直线执行。正常依赖为 `A → B → C → D → J 预审（触及风险／数据时）→ E → F → G → I → J 范围复核 → K → L → H`；若实现范围未触及风险／数据，J 标记不适用并说明理由。M 只在跨项目候选晋级时执行。任何必测项 FAIL 都阻断 H；NOT RUN 必须写明原因、风险所有者，并由用户明确接受延期，否则同样阻断。J／K 发现的问题必须关闭或形成带所有者的明确延期，不能只写“已检查”。

### Gate A：项目 brief

在设计或代码前写清：目标用户、是否公开、核心任务、特色体验、失败成本、明确非目标、目标设备。缺一项就不进入方案选择。

### Gate B：证据与现状

读取现有设计／协议权威文档，检查工作区，运行当前产品或查看最新真机证据。无法看到的状态标为假设，不凭代码想象视觉。

### Gate C：边界拆分

把需求拆成 UI、交互、数据、同步／协议、迁移、硬件六层。每层分别写“会改／不会改／需要另行批准”。

### Gate D：方案与验收先行

对非机械决策给出 2–3 个受约束方案。涉及配色时先建立操作重要性地图，并列出画布、chrome、卡片、文字、边界、状态和重点动作的语义归属。先写验收矩阵和极端样本，再选择实现；禁止实现完成后才发明标准。

### Gate E：最小纵向切片

先实现一个可真机验证的完整切片，包含默认、长内容、失败、深色和目标字体倍率。切片通过后再推广到其它页面。

### Gate F：自动验证

运行最小相关测试；交付前运行单元测试、lint、构建和仓库文档检查。新增 token 应有使用点，新增规则能自动检查时必须进入工具／CI。

### Gate G：真机验收

构建当前工作区 APK／固件，在目标设备验证视觉、手势、inset、字体、地图动态行为和硬件状态。颜色变更必须覆盖浅／深模式及主页面／表单／状态页，检查完整合成而不是单个色块。每项记录 PASS／FAIL／NOT RUN，不用“应该没问题”。

### Gate H：冻结与记忆

只有 G、I、适用的 J、K、L 已通过或获明确风险延期，用户明确验收后，才更新权威文档，把规则标为 `accepted` 并注明 `supersedes`。随后才写记忆扩展；未通过的方案不进入记忆。跨项目个人偏好须经第二项目或用户明确提升。

### Gate I：规则分类

每条新增规范性规则登记 E／P／B／C、适用平台／产品模式、状态、证据、例外、晋级条件和 `supersedes`。B 必须写项目名。没有类别的规则不得进入 DESIGN、记忆或 skill。

### Gate J：风险与数据

实现前预审权限最小化、凭据／日志脱敏、数据保留与删除、覆盖、备份恢复、离线、重复提交、冲突、超时、部分成功、迁移失败和回滚；真机后复核实现是否扩大范围。个人工具不得跳过适用项。

### Gate K：可操作性与兼容

按 Gate A 已获用户确认的范围检查对比度、字体倍率、非颜色状态、焦点／语义、减少动态效果、支持系统版本、设备形态、语言、动态／静态色和异常网络；缩小范围必须记录理由和风险。语义标签、触发反馈与恢复不可豁免。隐藏手势可作为低成本、可恢复、非核心新奇功能的唯一入口；核心、高成本或不可逆能力必须有显性备用入口。

### Gate L：发布证据

记录基础 commit；若工作区未提交，另记录 `git status`、dirty diff／patch 指纹；同时记录构建配置、APK／固件 hash、设备／系统版本、测试版本、已知未验证项和回滚方式。提交不是验收前提，但产物必须能唯一对应到“基础 commit + 工作区差异”。

### Gate M：候选晋级

在天色 beta 使用候选规则前，先写假设、反例、通过条件和失败后的归属。天色 beta 验收后，或用户基于现有证据明确决定时，才可晋级为 P；否则继续作为明确命名项目的 B 类，或保留为 C。

## 8. 从规范到个人 skill

个人开发 skill 不直接从一次项目总结生成。建议路径：

1. BugChecking 本轮每阶段验收后登记项目规则。
2. 在天色 beta 中使用同一开发流程，但允许它形成不同视觉世界。
3. 对照两个项目，筛出真正跨项目稳定的偏好与只属于单一产品的特征。
4. 由用户确认哪些规则提升为个人偏好。
5. 创建 skill，包含：触发描述、项目 brief 问题、选择倾向、反模式、分层审批、真机矩阵、记忆晋级协议和示例。
6. 用两个既有项目做回放测试：skill 不得把 BugChecking 的地图／柔糖机械复制到天色 beta，也不得把天色 beta 的特征反向污染 BugChecking。

## 9. 当前待验证的候选个人倾向

- C-04：图标优先和少说明文案是否适用于除个人工具外的公开项目。
- C-01／C-02：明亮柔和、带色深色表面是否是跨项目偏好，还是 BugChecking 专属。
- C-05：特色次要动作持续可见是否在天色 beta 仍成立。
- C-03：系统字体优先是否会被天色 beta 的品牌需求推翻。
- C-06：隐藏手势是否可作为高频核心功能的可选加速器；显性备用入口仍是底线。

这些问题在天色 beta 得到证据前，不写成跨项目强制规则。
